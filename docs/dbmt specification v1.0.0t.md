# 1. On versioning
- This specification is marked `v1.0.0t` with a `t` in the end for TODO. This means it's undergoing much construction work and not yet stabilized.

# 2. Intro

This language extends [dbml][1] (1) (github: [holistics/dbml][2] (2)).

See the new features added in [New Features](#3-new-features).

# 3. New Features

## 3.1. File inclusion

Status: Pending

We need to be able to break down our work into multiple units. This syntax allows other `*.dbmt` files to be included into one final result:

```dbmt
.include "path/to/other.dbmt"
```

Content of files being included must be valid `*.dbmt` files. Inclusions must only work with files that are self-contained syntactically.

For example, you should not be able to include within a table definition, because that would be a file with incomplete grammar.

File includes must allow multiple levels of inclusion without any set limit.

cyclic includes are not allowed and must flag an error.

## 3.2. Custom data types

Status: Pending

A new data type can be defined via

```dmbt
.type {new_type_name} {known_type}
```

This can become relevant when we want to haved shared validation logic for our database operations. For example, 

```dbmt
.type HP integer
```

would allow us to define verification on the application side whenever an `HP` field is written, read, deleted, etc. It will also expose that type for the application logic, rather than a generic integer.

## 3.3. Triggers

Status: Pending

These are events the software understands and can route actions to respond on their occurance.

| Trigger  | Event Data     | Meaning                                                                        |
| -------- | -------------- | ------------------------------------------------------------------------------ |
| insert   | table, row     | Occurs whenever a database insertion operation is performed on a table.        |
| update   | table, row     | Occurs whenever a database update operation is performed on a table row.       |
| delete   | table, row     | Occurs whenever a database delete operation is performed on a table row.       |
| write    | table, row     | Occurs on all write operations insert, update, delete.                         |
| read     | table, columns | Occurs when a selection of columns are fetched from a table.                   |
| init     | database       | Occurs on database initialization at the beginning of program execution.       |
| shutdown | database       | Occurs when the database module is issued a shutdown command by user software. |
| cust     | user defined   | User defined trigger. See [Custom Triggers](#331-custom-triggers).             |


### 3.3.1. Custom Triggers

In addition to the triggers defined in [Triggers](#33-triggers), [User Software](#42-user-software) can define their own triggers. These will be driven by the user and subscribed to by [Generated Library](#46-generated-library).

The syntax is 

```
cust({trigger_name})
```

where
  - `{trigger_name}` is an [Identifier](#45-identifier).

When a custom trigger is detected in the dbmt file, the appropriate subscribing signals will be generated by [Generated Library](#46-generated-library). [User software](#42-user-software) can then publish to `{trigger_name}`.

## 3.4. Signals

Signals are events routed to one or more triggers via the `%signal` [percent syntax](#44-percent-syntax).

The syntax is

```dbmt
%signal {symbol} {{trigger_type}=[{trigger}, ...] ...}
```

where
  - `{symbol}` is an [Identifier](#45-identifier) representing the name of the signal that [User Software](#42-user-software) can [subscribe](#48-signal-subscribing) and [publish](#49-signal-publishing) to.
  - `{trigger_type}` is an [Identifier](#45-identifier) defined in [Signal Trigger Types](#341-signal-trigger-types).
  - `{trigger}` is one of the triggers defined in [Triggers](#33-triggers) or custom defined by [User Software](#42-user-software) as explained in [Custom Triggers](#331-custom-triggers).
  - The `{trigger_type}=[{trigger}, ...]` argument itself may be used one or more times, up to the number of possible trigger types. Repetition of trigger types is not allowed and would flag an error.

A signal must be associated with a type, a table, or a column. Otherwise, an error is flagged.

Signals may chain (one per line) preceding an associated item.

Signals must have unique symbols in a signal chain preceding an associated item, one unique symbol per signal line.

See [Signal trigger type priority queue](#343-signal-trigger-type-priority-queue) for rules on  chaining.

### 3.4.1. Signal Trigger Types

Status: Pend


| Trigger Type | Meaning                                                                                                                                                                                                                                                                                           |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| notify       | When a trigger in given list occurs, notify the subscriber configured by [User Software](#42-user-software).                                                                                                                                                                                      |
| default      | When a trigger in given list is set to occur, current value associated with event is sent to [User Software](#42-user-software) which must respond with a value to replace it with. This must not chain with `override`.                                                                          |
| override     | When a trigger in given list is set to occur, current value associated with event is sent to [User Software](#42-user-software) which must respond with a value to replace it with. This must not chain with `default`.                                                                           |
| allow        | When a trigger in given list occurs or is set to occur, permission requested to [User Software](#42-user-software), which may respond with `OK (0)` or any other error code that will be issued as an error according to [User Software](#42-user-software) following a `shutdown` trigger event. |
| warn         | When a trigger in given list occurs or is set to occur, filter is requested to [User Software](#42-user-software), which may respond with `Keep (0)` or `Skip (1)` to log a warning according to a mechanism configured by [User Software](#42-user-software).                                    |
| trace        | When a trigger in given list occurs, filter is requested to [User Software](#42-user-software), which may respond with `Keep (0)` or `Skip (1)` to log a trace according to a mechanism configured by [User Software](#42-user-software).                                                         |


Note that when we write `OK (0)`, we just mean the value `0`. The rest is added for clarification.

Note that for columns marked with `override` signals, the user must not be able to provide a value when performing
operating on the database as they are guaranteed to be overriden.

To allow the user the option to bypass compute, use `default` instead of `override`. This must check if the user
provided a value, and if not, computes it.


### 3.4.2. Provided Symbols

Provided symbols are common computations provided by [Generated Library](#46-generated-library) and do not need to be defined by [User Software](#42-user-software).

| Symbol       | Effect                                                               |
| ------------ | -------------------------------------------------------------------- |
| get_date_now | Calculates the current date now according to user timezone settings. |

### 3.4.3. Signal Trigger Type Priority Queue


For `notify`, there can exist many [subscribers](#48-signal-subscribing). Events are simply published on trigger.

For [signal trigger types](#341-signal-trigger-types) other than `notify`, [User Software](#42-user-software) must provide a [server](#410-clientserver-pattern) to respond to requests made by [Generated Library](#46-generated-library).


For the remaining trigger types, 

There is a priority queue in execution. [Generated Library](#46-generated-library) combines all non-notify 
signals and executes them synronously in a queue.

The queue goes as follows:

1. Handle `override` (or `default`, they are mutually exclusive) trigger type first
2. Handle `allow` on the possibly overriden value
3. Handle `warn`.
4. Handle `trace`.

For non-notify signals, there must exist zero or one [subscriber](#48-signal-subscribing) per [signal trigger type](#341-signal-trigger-types) for a given set of [triggers](#33-triggers).

Here is an exampled of chained signals:

```
%signal log_inserts notify=[insert]
%signal get_date_now override=[insert]
%signal is_valid_timestamp allow=[insert, update]
%signal warn_should_not_change_timestamp warn=[update]
.type timestamp_t varchar
```

With this, any column using the type `timestamp_t` will associate the defined signals. All chained signals will
be carried out sequentially. Notify will always happen first. Then value override, followed by validation, followed by logging on validated action will ocur.

Note that `get_date_now` is a [provided symbol](#342-provided-symbols), so [Generated Library](#46-generated-library) ships with it and must call it directly. For non-provided symbols, [User Software](#42-user-software) is expected to
serve a response and an error code for the given symbol.


## 3.5. Computed Fields

Some fields are computed at some time and shouldn't be manually inserted. A popular example is `created_on` and `updated_on` which are computed on insert and both insert/update events respectively. 

We use an override [signal](#34-signals) to write them.

```dbmt
Table MyTable {
	%signal get_date_now override=[insert]
	created_on string
	%signal get_date_now override=[insert, update]
	updated_on string
}
```

## 3.6. Virtual Fields

Some fields are always computed and shouldn't actually be written to the database. We call them virtual fields. [User software](#42-user-software) may compute them on fetch based on current table and row information retreived.

The syntax is

```
%virtual {symbol}
```

where
  - `{symbol}` is an [Identifier](#45-identifier) used to compute the virtual field on fetch. This may be a [provided symbol](#342-provided-symbols) provided by dbmt, or it may be defined by [User Software](#42-user-software).

Here's an example:

```dbmt
Table BodyPhysics {
  mass float
  acceleration float
  %virtual f_equals_m_a
  force_applied float
}
```

## 3.7. Data Access

Status: Pend

| Access Type | Meaning                                                                                                                                  |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| fixed       | Table only allows fetch, unless in [admin mode](#47-admin-mode).                                                                         |
| immutable   | Table only allows fetch and insert operations, unless in [admin mode](#47-admin-mode).                                                   |
| mutable     | Table only allows fetch, insert, and update operations, unless in [admin mode](#47-admin-mode).                                          |
| ephemeral   | Table allows all operations fetch, insert, update, and delete. This is the only access configuration in [admin mode](#47-admin-mode). |


In case data access rules are violated, a `shutdown` event is triggered and an error is flagged according to a mechanism defined by [User Software](#42-user-software).

Data access [percent syntax](#44-percent-syntax) commands are provided for each access type.

Data access may only be configured on a table. For example,

```
%mutable
Table MyTable {
  ...
}
```

## 3.8. Not Nullable by default

Status: Pend

The specification for [dbml file format][1] states the following:

> null or not null: mark a column null or not null. If you ommit this setting, the column will be null by default

dbmt will change this expectation. Whether a field is null will be encoded in the type system of [Generated Library](#46-generated-library), and so all fields are not null by default. Use `[null]`, the same column configuration syntax of `dbml` to mark a field as nullable.

## 3.9. Option to always ensure uniqueness

The specification for [dbml file format][1] states the following allows a column configuration `[unique]`. 

dbmt adds an additional configuration `%ensure_unique`.  

This must be applied to a column marked `[unique]` or an error is flagged. This will make it so that whenever the table is fetched or written, the uniqueness condition is checked by [Generated Library](#46-generated-library). 

`%ensure_unique` is opt_in for performance purposes.

`%ensure_unique` can only be associated with a column. An error is flagged otherwise.

## 3.10. Option to always ensure correct join relationships

Status: Pend

As defined in the specification for [dbml file format][1],

```
There are 4 types of relationships: one-to-one, one-to-many, many-to-one and many-to-many

    <: one-to-many. E.g: users.id < posts.user_id
    >: many-to-one. E.g: posts.user_id > users.id
    -: one-to-one. E.g: users.id - user_infos.user_id
    <>: many-to-many. E.g: authors.id <> books.id
```

Relations like zero-to-many are inferred from the nullability condition.

By the [Not Nullable by default](#38-not-nullable-by-default) policy, relationships are one-to-many or many-to-one rather than zero-to-many or many-to-zero by default. This can be changed by explicitly declaring a field null.

Using the option `%ensure_join_relation` for a column will trigger [Generated Library](#46-generated-library) to always ensure those condition match fetch or write.

`%ensure_join_relation` can only associate with a column. An error is flagged otherwise.

# 4. Concepts

## 4.1. Schema

By schema, we mean the entities of the database and their interrelations. Together, they form a schema for the data of the system they describe.

This can also go by the name of [ontology][3], as it describes what the system data model is.

## 4.2. User Software

This is the direct user of the generated database library sourced by the dbmt [schema](#41-schema) file.

## 4.3. Dot Syntax

Some commands we are introducing use dot syntax. For example [file inclusion](#31-file-inclusion) and [custom data types](#32-custom-data-types).

Those are commands that apply at the global level.

Their syntax is

```
.{command} {{arg} ...}
```

where
  - `{command}` is an [Identifier](#45-identifier) representing the  name of the command.
  - `{arg}` is space-separated argument strings parsed according to the command syntax.

Every command has its own number of arguments. If it is not provided correctly, an error must be flagged.

## 4.4. Percent Syntax

Some commands we are introducing use percent syntax. For example, [Signals](#34-signals).

The syntax is 

```
%{comamnd} {{arg} ...}
```

where
  - `{command}` is an [Identifier](#45-identifier) representing the  name of the command.
  - `{arg}` is space-separated argument strings parsed according to the command syntax.

Percent Syntax is similar to [Dot Syntax](#43-dot-syntax) in form. However, it also is additionally associated to the item on the line after it.

Note that if the next item is also a Percent command, it will apply on a chain to the item after the last Percent command.

For example,

```
%command1
%command2 some args
%command3
Table MyTable {
  ...
}
```

Commands `command1`, `command2`, `command3` all apply to `MyTable`.

Two percent commands cannot occupy the same line. A percent command cannot be inlined next to an item. It must occupy a line of its own.


## 4.5. Identifier

These are strings that are similar to C function names in syntax rules.

- No spaces in the string
- Does not begin with a number
- May contain numbers, letters, or `_`

This is also identical to the constraints for [str.isidentifier][5] in python.

## 4.6. Generated Library

This refers to any code that is autogenerated given a dbmt [schema](#41-schema) file.

## 4.7. Admin Mode

When activated, the [Data Access](#37-data-access) feature is disabled, and all data can be written freely.

## 4.8. Signal Subscribing

Inspired by the [publish/subscribe pattern][4] (4).

Subscribers receive information from publishers, but do not block them. Publishers publish messages to topics, which in our case are the symbol names the user defines with signals.

For the `notify` [signal trigger type](#341-signal-trigger-types), it works just like in the pattern. Many subscribers may be notified by events published to the symbol defined by the user.

Other signal trigger types require the publisher to await a response from the subscriber and so they break this pattern and follow a [client/server pattern](#410-clientserver-pattern) instead.

## 4.9. Signal Publishing

Inspired by the [publish/subscribe pattern][4] (4).

[Generated Library](#46-generated-library) in this case publishes events from the specified triggers to the user defined symbols. 

## 4.10. Client/Server Pattern

A server provides a service and uptime to respond to one or more clients at any time. 

A client makes a request to the server to fulfill some service.

In constrast to [signal subscribing](#48-signal-subscribing) where pubishers do not need to know
subscribers and information is just posted to topics, 
here the two entities must interact in a sequential manner. 

1. Client sends a request denoted by the [signal symbol](#34-signals)
2. Server responds with output to the client and a status code, where 0 is success and 
   otherwise is some error code.
